## 2. 新版剩余问题

### P1 · G1 设计评审前解决（不阻断 G0）

| # | 问题 | 代码 / 文本证据 | 影响 | 建议 |
|---|---|---|---|---|
| **P1-1** | **确定性投影键在现有 `token_usage` 上会主键冲突** | 方案 §5 L94「以 (companyId, attemptId, settlement) 构造稳定 eventId…保证幂等」。实际 `JdbcUsageStore.java:37` 主键是 `(company_id, id)`，L70-75 是裸 `INSERT`（重复抛 `DuplicateKeyException`，不是幂等 no-op）；`TokenUsageService.java:94-105` 一次 `record()` 的 payload 是**数组**，for 循环每条写一条 `UsageRecord`——若共用同一 eventId，第 2 条起即冲突；`UsageContext.java:10` 无 attemptId/settlement/companyId，投影键输入拿不到；ClickHouse DDL（L44-51）MergeTree 不去重，重复 eventId 会追加两行 | 从「随机 ID」改成「确定性 ID」并不自动得到幂等；直接替换会把一次正常的多模型用量上报变成 500 错误 | 明确三件事：① 投影键加序号后缀 `(companyId, attemptId, settlement, lineNo)`；② 新增独立投影通道（如 `ProjectionRecorder`），不改现有 `record()` / `recordCost()` 的 CLI TOKENS 调用链，避免 5+ 个上游路径拿不到 attemptId；③ 明确 ClickHouse 侧去重策略（引擎或读时去重）；MySQL 侧把 `save()` 改为 `INSERT IGNORE` 或 `ON DUPLICATE KEY UPDATE` 并校验参数摘要 |
| **P1-2** | **准备金承接未决占用的财务闭环不完整，且 SLA 自相矛盾** | §4 L80「员工冻结最多 2 个工作日，届时由准备金承接未决占用、补回员工余额，原尝试仍待核对；迟到证据通过冲正结清」；§5 L100 仍写「建议 1 小时未决告警、下一个工作日内完成核对」——1 日 vs 2 日冲突。代码侧：`gateway_account`、冲正、待核对状态机**全部不存在**，属新建（全库零匹配） | 若迟到证据显示 A<R，准备金已代付 R、员工余额已补回，差额 R−A 冲谁的账？若冲员工则余额可能变负；若冲公司则成了公司吸收供应商多收。A>R 同理。准备金不足时无降级路径。员工实际是无息占用公司资金，财务需确认可接受 | 明确三条规则：① 准备金承接的是**员工的确定性占用上限**，员工余额补回后不再因迟到证据变动；② 所有 R−A / A−R 差额只在公司准备金/专用账户与供应商之间清，通过 `gateway_ledger` 追加分录；③ 准备金不足时暂停新轮并告警，不得临时改成员工继续冻结。统一两处 SLA 口径 |

## 3. 结论

这一稿已经达到「可交给开发执行」的成熟度。三轮迭代的收敛轨迹很清楚：第一稿补机制（turnId、TTL、拓扑、硬限额证据），第二稿补判据（误拒率、body 边界、输出下限、取证能力），第三稿补实施细节（轮次状态机、投影键、准备金、409 语义）。现在剩下的两项 P1 不是「方案没想清楚」，而是「方案想清楚了但落到现有代码会踩坑」——属于实现评审而非设计评审。
