## 2. 新版剩余问题

### P1 · 应在 G0/G1 补齐

| # | 问题 | 方案原文 / 缺口 | 影响 | 建议 |
|---|---|---|---|---|
| **P1-A** | **误拒率只有「记录」，没有通过线** | §4 L49「测试样本验证契约、记录误拒率，不把有限样本当成数学保证」；G0 L84 要求输出「误拒率与分母」，但全文无阈值 | 上一轮 P0-4 的核心是「保守上界导致误拒率极高、产品不可用」。新版解决了「怎么算上界」，但没解决「算出来多差才不许开」。G0 会收齐数据却无法判定 | G0 定义：样本量下限 + 误拒率上限（建议 ≤5%，按公司实际请求分布取样），超线则该组合不进硬限额试点；同时写明分母口径与取样方法 |
| **P1-B** | **完整请求体读取与内存/大小上限缺失** | §4 L47「仅针对必要字段读取和受控改写输出上限」vs L49「纳入工具定义、工具结果、模板、推理、缓存与附件」——精确计数必须读**完整** body，二者表述冲突；全文无 body 大小上限、OOM 防护、超大附件降级 | 一次带大附件或长工具结果的请求可能把 servlet 线程与堆打满；实测时才发现 | 明确 body 上限（按模型上下文或固定 MB）、超限策略（拒绝 / 转 shadow / 只做计费输入计数），并规定读 body 的流式解析与临时落盘策略；修正 L47 措辞 |
| **P1-C** | **输出上限夹紧会破坏工具调用与推理** | §4 L49「输出上限向下夹到可用空间」、L72「用完时停止后续生成、保留部分回复」 | 夹紧到很小时，工具参数 JSON 被截断，`finish_reason: length` 会让 CLI 解析失败并重试；推理模型的 reasoning 在被截断时答案质量崩溃。「保留部分回复」只覆盖纯文本场景 | 定义**最小可用输出上限**：低于该值时不出站（返回 QUOTA_EXHAUSTED），而不是夹紧后仍发；工具调用中的请求单独规定是否允许夹紧；G0 用真实 CLI 验证截断后的行为 |
| **P1-D** | **warm session 换令牌的可行性未验证** | §3 L32「warm session 若不能替换环境，则结束旧子进程、用新令牌恢复会话」 | 依赖 CLI 的会话恢复能力；不是所有 runner 都支持 `--resume` 或等价机制。结束子进程还可能丢失本地状态。G0 L84 只要求对 DeepSeek 证明，G4 的 11 家 runner 逐个验证意味着试点期后仍可能爆雷 | G0 输出「runner × 是否可换令牌 × 换后会话保真度」矩阵；不支持的组合在受管模式中显式禁用 warm session（每轮重启进程），并把体验代价写进产品说明 |
| **P1-E** | **聊天路径的 turnId 语义未定义** | §3 L30 只明确「任务内一次调度执行的技术性重试保留 turnId」；未说 `ChatService` 的 `failover()` 换 Key 重试、`MODEL_HOPS=2` 换模型重跑是否保留 turnId；也未说同轮多令牌并存时的撤销顺序 | 若聊天重试被当成新一轮，同一用户动作会重复申请上浮；若保留但旧令牌未及时撤销，会出现同轮两把有效令牌 | §3 补一句统一规则：「聊天路径的技术性重试与任务同规则——新 runId + 新令牌 + 继承 turnId，旧令牌在 runner 结束时撤销」；G0 加一条 failover/换模型场景的令牌与 turnId 断言 |
| **P1-G** | **对账 SLA 依赖未验证的供应商能力** | §5 L68 定时按 request_id 取证，供应商无能力则转人工，SLA「1 小时告警 / 下一个工作日内核对」；§8 L102 把「供应商是否支持逐请求对账」列为待工程验证 | 若 DeepSeek 不支持按 request_id 查 usage，所有断流/取消/崩溃都转人工，十人公司每次都要查账单——运营不可持续；「冻结 R 不扣」会长期占用员工余额 | G0 必须把该能力验证作为**阻断项**：支持则接入自动对账；不支持则在 G0 定义替代证据（账单导出周期、时间窗估算规则）并重写 SLA，否则 G2 不应开放给真实员工 |

## 3. G0 放行条件（建议作为硬门槛）

G0 结束时必须**同时**拿到以下三项，否则不得进入硬限额试点：

1. **误拒率通过线已定义且达标**（P1-A）：样本量、分母口径、上限值写进 G0 报告。
2. **输入计数方案可复算 + 请求体边界已确定**（P1-B/P1-C）：含 body 上限、最小可用输出上限、工具调用夹紧策略，并有真实 CLI 的截断行为证据。
3. **供应商逐请求 usage 取证能力已验证**（P1-G）：支持则给出接口与字段；不支持则给出替代证据与重写的 SLA。

P1-D/E 可在 G0 出矩阵与规则、G1 前完成断言即可，不阻断 G0 启动。

## 4. 结论

这一版从「有想法的评审稿」变成了「可执行的实施依据」：拓扑、令牌、账本守恒、迁移三态、验收阈值都落到了可测的形式，且诚实标注了未实测项。上一轮的 18 项没有被敷衍处理，而是逐条改到了正文——这一点值得肯定。

剩余问题的共同特征是：**方案规定了「要证明什么」，却没有全部规定「证明到什么程度才放行」**。P1-A、P1-B、P1-G 都属于这类「判据缺口」。把它们补进 G0 的退出条件，这份方案就可以作为开发依据直接使用。

建议动作：按上述 G0 放行条件补一页「G0 判据表」，然后开工；P1-D/E 在 G1 设计评审时闭环。
