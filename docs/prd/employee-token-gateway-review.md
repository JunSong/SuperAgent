## 1. 一句话结论

方向正确，可以按「有条件通过」推进；**先合并两份网关方案、用 G0 证明 DeepSeek 硬限额可行性，再开工 G1**。

---

## 2. 做得好的地方

1. **产品边界清楚**  
   内建 Java 网关、不用 LiteLLM、token 整数、UTC 月、跨模型共用额度、Key 只在控制面——都符合 README / architecture 的既定判断。

2. **账本设计对路**  
   账户 / 尝试 / 分录拆开、先预占再出站、流式期间不持锁、跨月回原月结算、幂等键、冲正只追加——这是能扛并发的正确形态；比现有 `QuotaService`（事后汇总 + 1 分钟缓存软检查）更接近「企业额度」语义。

3. **责任人模型对**  
   `agentId` 与付费 `userId` 分离、任务交接不改历史归属、系统作业走系统账户——避免数字员工把人账搅乱。

4. **诚实的硬限额定义**  
   承认「字符÷常数」不能承诺硬上限、`A > R` 不截断只暂停组合——这比假装能精确控量更稳妥。

5. **回滚立场更正确**  
   明确「恢复直连 = 绕开限额 + 重新暴露 Key，不能自动当故障恢复」——比另一稿「秒级切回直连」更符合本产品目标。

## 4. 主要风险与设计缺口

### 4.1 硬限额 R 是整案技术风险最高点

预占依赖「可靠输入上界 + 强制输出上限」。DeepSeek CLI 路径上，工具定义、附件、模板是否都能在发请求前得到可验证上界，目前未证实。若 G0 拿不到可靠 R，硬限额公司只能拒组合——试点面可能塌掉。

**要求：** G0 退出条件应显式含：

- 至少一种可验证的 R 算法
- 失败样本矩阵

拿不到则 G2 只做软预占（超额告警 / 事后停），不宣称硬封顶。

### 4.2 G2 上浮规则偏复杂，易卡 UX

「可用被占满时新轮等待结算，不提前判耗尽」没有超时、队列长度、取消语义。并发 turn、工具往返、`B+F` 夹紧输出——状态机不小。

**建议：** MVP 先 **F=0**（文档已写原并发用例按 F=0）；上浮作为 G2.1，并补「等待最长 N 秒 → 明确业务码」。

### 4.3 与 `QuotaService` / `token_usage` 双轨未钉死

今日公司月额度在 `Company.monthlyTokens` + `QuotaService.checkTokens()`。受管租户启用后需明确：

- 谁是主账？
- 旧检查是否旁路？
- 网关结算与 CLI `TOKENS` → `TokenUsageService.record()`（随机 UUID，非幂等）如何避免双计？

**要求：** 写清状态机：`legacy | shadow | gateway_primary`；受管租户禁用软配额入口；报表只认已结算流水的稳定事件 ID。

### 4.4 令牌模型仍绑同机进程

`McpGrants` 是内存 Map。本稿复用签发时机合理，但「model 与 MCP 权限区分」要落到独立 grant kind / scope，且接口先抽象成 `RunTokenResolver`（另一稿已有），否则以后 Worker 分离会整段重写。

### 4.5 Token ≠ 钱已承认，运营面还不够

跨模型一比一扣 token，管理员容易把「token 预算」当「人民币预算」。至少在 UI / 审计上强制展示：模型、用量、估算金额分列；公司系统账户成本建议公开——同意，且应进 G2 验收，不只是文末备注。

### 4.6 「独立部署验收」措辞易误解

读起来像网关可独立进程；实际是「干净环境只起 SuperAgent jar」。与 architecture「先进程内、后可拆」一致，但建议改成「单机一体验收」，避免和 G5 独立部署混淆。

### 4.7 分层细节要锁死

`superagent-gateway` L3 只依赖 platform / core / api；与 `superagent-cost` 同层不互依、经 core 契约消费事件——正确。实现时禁止 gateway pom 拉 cost；计价继续经接口下沉。
