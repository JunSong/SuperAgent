## 3. 剩余风险（非阻断）

| # | 事项 | 说明 |
|---|---|---|
| R-1 | **担保份额对有效预算的占用未量化** | §5 L100 准入时锁定可覆盖 R 的公司担保份额，R 是「输入上界 + 完整输出上限」，可能远大于实际 A。未决尝试多时，公司可用余额被担保锁死，员工新轮会被 QUOTA_INSUFFICIENT 拒绝——但原因不是钱花完，而是对账未闭环。建议在 G2/G3 压测里加「担保占用率」指标与上限，超过阈值暂停新轮并告警（方案已有「担保不足暂停」，但缺「占用率过高」的观察面） |
| R-2 | **准备金担保与 A>R 的双重承担边界** | L102 说 A>R 差额由准备金承担并停组合；若同一组合已有多笔未决尝试且担保份额不足，差额会转为 D。G3 演练只给了单笔 R=60 的三种 A，建议补一笔「多尝试并发 + A>R + 准备金不足」的组合用例 |
| R-3 | **工作日日历未落到配置** | §5 L100「工作日按公司约定日历」，但 §6/§7 未写日历从哪来、SaaS 多租户下如何配置。若公司未配置，SLA 无法计算。建议明确默认 UTC 或中国法定工作日，并纳入公司设置 |
| R-4 | **真值来源的授权依赖** | §4 L76 误拒率真值依赖「供应商 usage 或可信计数接口」；若 G0 拿不到授权，误拒率无法判定，硬限额不能开。这已是方案明说的分支，只需在 G0 启动前确认授权到位，避免测试阻塞 |

四项均为运营/压测层面的补充，不改变方案可执行性。R-1/R-2 可在 G2/G3 测试用例中顺带补上，R-3/R-4 是启动前确认项。

## 4. 结论

四轮迭代到这里，方案已经成熟：

- 第一轮把「想法」变成「机制正确」；
- 第二轮把「机制」变成「可测判据」；
- 第三轮把「判据」变成「实现细节」；
- 第四轮把「实现细节」变成「财务闭环 + 演练数值」。

当前版本与代码现状的关系是清楚的：哪些沿用（TokenUsage 口径、BusyException 409、MergeTree 无唯一约束、双后端切换）、哪些新建（gateway 模块、账本三表、独立投影通道、QUOTA_* 细分码、准备金与担保）。没有含糊的「沿用」措辞，也没有把新建能力说成已有。

**建议：按 v2.1 启动 G0，并把 R-1～R-4 作为 G0/G1 的补充观察项纳入测试计划。** 这四项不设阻断门槛。
